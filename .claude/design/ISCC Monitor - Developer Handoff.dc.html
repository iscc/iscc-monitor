01

Scope & architecture

Three product surfaces. Two live on each monitor instance and must render as plain server HTML/CSS with no JavaScript; in-browser re-verification is a progressive enhancement layered on top. The third is a separate static site on a domain no monitor controls.

Hard rule

A & B must be useful and readable with no JS at all. Do not hard-require an SPA framework for them. The verifier app (C) may be fully client-side.

Out of scope — do not build

Cosigning / cross-monitor compare · projection views (current owner / gateway URL) · auth / login / settings / write / config · operator deployment screens · authoritative Bitcoin verify in-page (download .ots, user runs ots verify).

02

The model everything hangs on

The monitor is a verifiable cache, not a trusted oracle. Reading a badge it rendered is not the same as the claim being true. Every screen keeps two trust tiers visually distinct — and tier 2 is always one action away.

Tier 1 · convenient
The monitor reports…

Server-rendered state. The default content. Visually muted / neutral.

build · plain SSR HTML
Tier 2 · authoritative
Your browser verified…

The WASM verifier re-ran the math locally. Visually elevated (ISCC-Blue border/fill). The killer feature.

build · WASM result, progressive enhancement

Failure mode to avoid: never let the monitor's green checkmark look like the final word. Tier 1 and Tier 2 must never collapse into one badge.

03

Invariants — conformance & must-keep

Hard constraints from the spec and ADRs. Each is satisfied in the Evidence Ledger design; keep it satisfied through implementation.

1 · Two trust tiers stay distinct

Tier 1 = muted server content; Tier 2 = ISCC-Blue–elevated WASM result. Present on the Certificate and the Independent-verification screen. Must-keep: never collapse into one badge; Tier 2 always one action away.

2 · Honest coverage, always

Every hub shows its monitored_since (size + time); the dossier states guarantees hold only from coverage start. Must-keep: never imply pre-coverage guarantees; a claim timestamped before coverage must say so.

3 · Five statuses distinct; frozen unmistakable & non-dismissable

frozen renders as a solid-red Exhibit (violation report), categorically different from the soft-tint caution of unresolvable/unverified. Must-keep: frozen clears only by manual operator review — never auto-heal or look transient.

4 · Color is never the only signal

Status = icon + label + distinct silhouette (check-circle / cloud-? / triangle / octagon / pause). Legible in grayscale and colorblind-safe — built for legal/audit screenshots. See the status reference (§5).

5 · The verifier app's independence is felt

Chrome links out to monitor.iscc.codes; the verification screen names which instance it audits (?monitor=) and states the checker is controlled by no monitor. Must-keep: the .codes ↔ .id distinction stays visible.

6 · The two anchors are never conflated

Bitcoin anchor (OpenTimestamps, pending → confirmed + block height) and comparison anchor (split-view reference for your own size,root) are separate, distinctly-labelled panels. "Anchoring" means Bitcoin only.

7 · Vocabulary discipline

Uses split view, self-consistency violation, coverage, deletion-as-new-record; "witness", "fork", "takedown" never appear. Full do/avoid list in §7.

8 · Server-rendered baseline

Dashboard and log browser work as plain SSR HTML/CSS; WASM re-verification is additive. No heavy SPA required for A & B.

9 · Operator / instance identity legible, no central authority

Chrome shows instance domain + operator + realm. Must-keep: nothing implies the data is more authoritative because of who hosts it — anyone can run an instance.

10 · Truthful empties & pending

"Anchor pending", "coverage just started — thin window", "hub offline · serving mirror" render as informative states, never as scary errors. See §6.

04

Screen specifications

Six screens, each delivered as its own standalone page file (named per card below). Routes are illustrative — match your router. Every screen carries the operator/instance chrome (logo · instance domain · operator · realm · verifier-app link) and the coverage discipline.

Surface ARealm index — dashboard / front doorGET /

Claim-lookup foregrounded ("Prove a specific claim is in the log") above a register of every hub in the realm — status, coverage, checkpoint, anchor, last activity. Glanceable and honest.

Data per hub

name · domain · status (1 of 5) · monitored_since (size) · latest checkpoint size · Bitcoin-anchor state · last-seen · → dossier. Plus realm: network, instance, operator.

States

degraded banner if any hub frozen · empty when monitoring just started · per-row thin coverage / offline·serving mirror flags.

Surface AHub dossier — incl. frozen ExhibitGET /hub/{domain}

One hub's full trust picture as a numbered document. §1 Identity (did:web) · §2 Coverage · §3 Latest checkpoint · §4 Bitcoin anchor · §5 Observation log. The Bitcoin anchor and the comparison anchor appear as distinct panels.

Browse a hub's records by sequence id, newest-first, with Newer/Older pagination and jump-to-sequence. Each row links to the single record. Pagination is link-based so it works with no JS.

Page fileISCC Monitor - Log Browser.dc.html
Data per row

seq · type (declaration / deletion / unknown) · iscc_id · logged time. Header: hub name, domain, total records, page range.

States

Surface BSingle recordGET /hub/{domain}/log/{seq}

One record's full detail, with Older/Newer stepping by ±1 seq and a link to prove inclusion. Must degrade gracefully for record types the monitor doesn't recognize.

Page fileISCC Monitor - Single Record.dc.html
Data

iscc_id · type + note.$schema · hub · position (seq) · logged time · raw bytes · → prove inclusion.

Type states

declaration · deletion (a new record — original preserved) · unknown (still indexed & provable; do not error).

Surface ACertificate of inclusion — proof resultGET /inclusion/{iscc_id}

A self-contained evidence document for a single claim, citation-friendly and screenshot-ready. The proof-bundle download and "verify independently" actions are primary.

Page fileISCC Monitor - Certificate.dc.html
Data (numbered clauses)

§1 subject iscc_id + position · §2 hub-signed checkpoint (size, root) · §3 inclusion proof (Merkle path) · §4 signing key (did:web + algo) · §5 Bitcoin anchor (block, time) · §6 all records for the id (full history incl. deletion).

States

found / not found (id not in log) · deletion present · anchor pending.

Proof bundle payload

{ hub-signed checkpoint, inclusion/consistency proof, record bytes, hub key, ots? }

Surface CIndependent verification — verifier appmonitor.iscc.codes/?monitor={url}&id={id}

The trust-critical moment: the WASM verifier recomputes the proof in the user's browser. Names which instance it audits; the result is framed "computed here". Includes the skeptical-client (size, root) split-view input.

Page fileISCC Monitor - Independent Verification.dc.html
Data / inputs

target instance (?monitor=) · input: an id / a pasted-or-dropped proof bundle / a user-supplied (size, root) · live state · verdict.

States

idle → verifying (per-step) → verified | mismatch · with / without a ?monitor target. Mismatch is a guided split-view alert, not a dead red error.

Hub status reference

Five statuses, conveyed by icon + label + distinct silhouette. All hubs are mirrored and served regardless of status — the monitor reports problems, it never goes dark on a hub. Reuse the HubStatusBadge component (see §8).

StatusPlain meaningToneTrigger / dev note
Signature valid, history consistent, root rebuilt.calmOnly verified checkpoints advance accepted state.
Can't fetch / parse the hub's did.json.cautionConfig / availability issue. Still mirrored.
Signing with a key its own did.json doesn't list.cautionInternally-broken hub. Distinct hue from frozen.
Caught rewriting its own history — a self-consistency violation.alarmHeadline event. Non-dismissable; manual review to clear.
Removed / paused in the realm registry.neutralNot a fault. Muted.

07

Vocabulary — binding

Use the canonical terms from CONTEXT.md. Where a precise term is unavoidable (checkpoint, inclusion proof), pair it with a plain-language gloss. The "avoid" column is binding.

Use
hub · monitor instance · verifier app · coverage / monitored_since · self-consistency violation · split view · verifiable cache · proof bundle · Bitcoin anchoring · comparison anchor · mirror · declaration · deletion · checkpoint · inclusion proof
Avoid
fork · equivocation · inconsistency (bare) · witness · trusted oracle · receipt (for bundle) · removal / takedown (for deletion) · anchor for the comparison role

A deletion is a new record, never a removal. "Anchoring" is Bitcoin-only.

09

Build notes & definition of done

Rendering

Dashboard + log browser: server-rendered, fully functional with JS disabled. Pagination via links (?from=). WASM verify enhances, never gates.

Verifier origin

Verifier app is a static site on monitor.iscc.codes — a different origin from any instance. Takes ?monitor={url}; one audited artifact for the federation.

Accessibility

Status legible in grayscale & colorblind-safe; AA contrast. Tap targets ≥ 44px on the inclusion result & verifier (mobile). Real timestamps visible.

Responsive

Desktop-first for dashboard & log browser; the Certificate of inclusion and the verifier must be usable on a phone (a declarer may check from mobile).

Definition of done
Two trust tiers visually distinct on every claim
Coverage window shown for every hub
Frozen unmistakable & non-dismissable
Status legible in grayscale (icon+label+shape)
Bitcoin anchor ≠ comparison anchor
Dashboard + log browser work with no JS
Deletion + unknown record types degrade gracefully
Verifier independence & target instance visible
