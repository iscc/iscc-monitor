# Next Work Package

## Step: Make `verify.wasm` reproducible — add `-buildvcs=false`, rebuild, re-pin `WasmVerifyHash`

## Advances
Closes the open **`critical`** issue *"`verify.wasm` is NOT reproducible — committed bytes embed a
`+dirty` parent-revision VCS stamp; the published hash cannot be regenerated"* (`issues.md`), which
preempts all milestone work. It is the prerequisite for the **WASM verifier upgrade** milestone Verify
criterion — *"the verifier artifact hash matches the published value; … reproducible build + published
hash + SRI pin (ADR-0003, ADR-0010)"* (`target.md`). The reviewer's `handoff.md` `**Next:**` names this
explicitly as the step to re-do *first*, before resuming the WASM `<script>` caller or the human-steered
M-UI parity work. An unreproducible hash pin is precisely the "green-but-wrong" trap `target.md` warns
about for hash-pinned artifacts: `TestWasmVerifyHashPinned` stays green today only because it never
rebuilds the artifact.

## Goal
Make `mise run build:wasm` deterministic so the committed `internal/web/verify.wasm` and its pinned
`web.WasmVerifyHash` can be regenerated byte-for-byte from a clean checkout — restoring the
reproducible-build / published-hash / SRI-pin contract that is the entire point of serving the artifact
byte-pinned. Without this, no CI or human rebuild-and-compare can ever pass, and the next WASM step would
build a `<script>` caller on top of a pin nobody can reproduce.

## Implementation Notes
- The single root cause (reviewer + Codex, both confirmed): the `build:wasm` task lacks `-buildvcs=false`,
  so `go build` embeds `vcs.revision` / `vcs.modified` / the `mod …+dirty` suffix. The committed blob was
  built `+dirty` at the parent revision (`strings internal/web/verify.wasm | grep vcs.` shows
  `vcs.revision=b2667f86…`, `vcs.modified=true`), so the documented task now emits a different `data`
  section (an 8-byte clean/dirty delta) and a different SHA-256 on every run.
- Keep `-trimpath` and `-ldflags=-buildid=` — they remain load-bearing (they kill GOROOT/module-path and
  buildid nondeterminism); `-buildvcs=false` is the missing *third* flag, not a replacement. The resulting
  `run` line should read:
  `go build -trimpath -ldflags=-buildid= -buildvcs=false -o internal/web/verify.wasm ./cmd/wasm`.
- The `env = { GOOS = "js", GOARCH = "wasm", CGO_ENABLED = "0" }` block on the task is correct; leave it.
- After editing the task, run `mise run build:wasm`, compute `sha256sum internal/web/verify.wasm`, and set
  `WasmVerifyHash` to that exact lowercase-hex value. The `web.go:78-85` doc comment already describes the
  task; keep it accurate (it need not change beyond the const value).
- The relevant Correctness rule (`learnings/web.md`): *"Any future committed wasm/binary artifact whose
  hash is published as an SRI pin MUST be built with `-buildvcs=false` or the published hash is
  unreproducible from a clean checkout."* This step is the canonical application.
- The committed `verify.wasm` is gated by `web.go`'s `//go:embed verify.wasm` (`web.go:148`), so the embed
  picks up the regenerated bytes automatically; no embed-directive change.
